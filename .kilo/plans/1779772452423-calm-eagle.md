# Omni-Channel Integration Plan

## Summary

Add real integration for Email, Twitter/X, Instagram, and WhatsApp channels. Refactor existing Telegram to use a unified channel abstraction. Currently only Telegram has actual inbound/outbound code — all other channels exist only as string labels in the DB.

## Key Decisions

| Decision | Approach | Rationale |
|---|---|---|
| Email outbound | **SendGrid** transactional email | Production-grade deliverability, webhook callbacks, free tier (100/day) |
| Email inbound | **SendGrid Inbound Parse** webhook | Receives parsed email as JSON, no IMAP polling needed |
| WhatsApp | **open-wa.org** (Node.js/Puppeteer) | No Meta Business verification needed. Runs as sidecar service with REST API |
| Twitter/X | **Userbot** via `tweety-ns` Python library | Automates Twitter web client, avoids X API v2 free tier limits |
| Instagram | **Userbot** via `instagrapi` Python library | Automates Instagram private API, avoids Meta Graph API requirements |

## Priority Order

```
Phase 1: Foundation + Telegram Refactor
Phase 2: Email (SendGrid)
Phase 3: WhatsApp (open-wa)
Phase 4: Twitter (userbot)
Phase 5: Instagram (userbot)
Phase 6: Unified Reply + Frontend
```

## Current State

- **Telegram**: Fully functional (long-polling inbound, triage notification outbound, resolve reply outbound) — but hardcoded with `if channel.lower() == "telegram"` checks in 3 places
- **Email, WhatsApp, Web, Phone, PlayStore**: Placeholder strings only in seed data
- **No channel abstraction**: No base class, no registry, no factory
- **No webhook endpoint**: All inbound is REST API or polling; no webhook route exists
- **No outbound message tracking**: No log of sent messages per channel
- **Config scattered**: Telegram token and API host are bare `os.getenv()` calls

### 1. Channel Abstraction Layer (`services/channels/`)

```
├── instagram.py           # InstagramChannel (instagrapi userbot)
├── whatsapp.py            # WhatsAppChannel (open-wa REST client)
└── webhook.py             # Unified webhook route (SendGrid + open-wa callbacks)
```

#### `BaseChannel` Abstract Class

```python
class BaseChannel(ABC):
    name: str                          # "email", "telegram", "whatsapp", "twitter", "instagram"
    display_name: str                  # "Email", "Telegram", "WhatsApp", "Twitter/X", "Instagram"
    supports_inbound: bool
    supports_outbound: bool
    inbound_method: str                # "polling" | "webhook" | "userbot"
    enabled: bool                      # Set at startup based on config presence

    @abstractmethod
    async def start(self) -> None      # Initialize listener/connection
    @abstractmethod
    async def stop(self) -> None       # Graceful shutdown
    @abstractmethod
    async def send_message(self, source_ref: str, text: str, **kwargs) -> bool
    @abstractmethod
    def is_configured(self) -> bool    # Check required env vars / sidecar health
```

#### `ChannelRegistry`

- Registers all channel instances at startup
- Only activates channels where `is_configured()` returns True
- `get_channel(name) -> BaseChannel | None`
- `list_channels() -> list[BaseChannel]`
- `send_response(complaint, text)` — dispatches to matching channel's `send_message()`
- `send_triage_update(complaint, ai_draft)` — sends triage assessment through the channel

### 2. Database Changes

#### New Table: `outbound_messages`

```sql
CREATE TABLE outbound_messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    complaint_id UUID REFERENCES complaints(id) ON DELETE SET NULL,
    channel VARCHAR(100) NOT NULL,
    source_ref VARCHAR(255),
    message_text TEXT NOT NULL,
    direction VARCHAR(20) DEFAULT 'outbound',
    status VARCHAR(20) DEFAULT 'pending',     -- pending/sent/failed/delivered/read
    provider_message_id VARCHAR(512),
    sent_at TIMESTAMPTZ DEFAULT NOW(),
    delivered_at TIMESTAMPTZ,
    error_message TEXT,
    metadata JSONB DEFAULT '{}'
);
CREATE INDEX idx_outbound_complaint ON outbound_messages(complaint_id);
CREATE INDEX idx_outbound_channel ON outbound_messages(channel);
```

#### New Table: `webhook_events`

```sql
CREATE TABLE webhook_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    channel VARCHAR(100) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    raw_payload JSONB NOT NULL,
    processed BOOLEAN DEFAULT FALSE,
    complaint_id UUID,
    error_message TEXT,
    received_at TIMESTAMPTZ DEFAULT NOW(),
    processed_at TIMESTAMPTZ
);
CREATE INDEX idx_webhook_channel ON webhook_events(channel);
```

### 4. Unified Webhook Endpoint

`POST /api/v1/webhooks/{channel}` — receives callbacks from SendGrid (email inbound) and open-wa (WhatsApp events)

- Verifies webhook signatures
- Validates payload
- Extracts message → creates complaint via the standard API path
- Returns 200 quickly, processes asynchronously
- Logs to `webhook_events` table

## Detailed Channel Implementations

### Phase 2: Email Channel (SendGrid)

**Dependencies:** `sendgrid` Python SDK (add to requirements.txt)

**Inbound (SendGrid Inbound Parse Webhook):**
- SendGrid forwards incoming emails to `POST /api/v1/webhooks/email` as JSON
- Includes parsed fields: `from`, `subject`, `text`, `html`, `attachments`
- No polling needed — completely event-driven
- `source_ref` = SendGrid message ID (`sg_message_id`), `customer_id` = sender email
- `attachments` stored in complaint JSONB

**Outbound (SendGrid Mail Send API):**
- `send_message()` sends via SendGrid's `Mail` helper
- HTML email template with Union Bank branding
- Tracks delivery status via SendGrid Event Webhook
- Retry logic for transient failures

**Flow:**
```
Customer email → SendGrid Inbound Parse → POST /api/v1/webhooks/email → create complaint → pipeline → SendGrid outbound reply
```

**Key files:**
- `services/channels/email.py` — EmailChannel class
- `api/routes/webhooks.py` — Handles SendGrid inbound webhook + signature verification

### Phase 3: WhatsApp Channel (open-wa)

**Dependencies:** No Python dependencies needed — communicates via HTTP with open-wa sidecar

**open-wa setup (separate service):**
- Node.js service running on `http://localhost:8081`
- First run: displays QR code for WhatsApp Web pairing
- Session persists across restarts
- Provides REST API: `GET /api/checkNumberStatus`, `POST /api/sendMessage`, `GET /api/getAllChats`
- WebSocket events for incoming messages (or polling `GET /api/getUnreadMessages`)

**Inbound:**
- Starts a daemon thread that polls open-wa REST API for unread messages
- OR uses open-wa webhook callback to `POST /api/v1/webhooks/whatsapp`
- Extracts message text from chat format
- Filters out non-customer chats (groups, broadcast lists)
- `source_ref` = WhatsApp chat ID, `customer_id` = sender phone number

**Outbound:**
- `send_message()` POSTs to `{openwa_base_url}/api/sendMessage` with chatId + content
- Supports text only initially

**Flow:**
```
WhatsApp user → open-wa (WhatsApp Web) → poll/webhook → create complaint → pipeline → open-wa sendMessage
```

**Key files:**
- `services/channels/whatsapp.py` — WhatsAppChannel (HTTP client to open-wa)
- `docker-compose.yml` — Add open-wa service container (optional)

### Phase 4: Twitter/X Channel (Userbot)

**Dependencies:** `tweety-ns` (Python Twitter automation library)

**Inbound:**
- Background thread polls for new @mentions using userbot session
- Filters for tweets directed at the configured Twitter handle
- Extracts tweet text (removes @handle mention)
- Deduplicates by tweet ID (persist last seen tweet ID)
- `source_ref` = tweet ID, `customer_id` = `@username`

**Outbound:**
- `send_message()` replies to the tweet or sends DM
- 280 character limit — truncates long messages, adds link to portal for full response
- Thread support: splits >280 char into reply thread

**Flow:**
```
Customer tweets @UnionBank → userbot detects mention → create complaint → pipeline → reply tweet
```

**Key files:**
- `services/channels/twitter.py` — TwitterChannel (tweety-ns client)

### Phase 5: Instagram Channel (Userbot)

**Dependencies:** `instagrapi` (Python Instagram private API client)

**Inbound:**
- Background thread polls Instagram DMs for new messages
- Session file avoids re-login on restart
- Filters for messages from non-own account
- `source_ref` = Instagram thread ID, `customer_id` = Instagram username

**Outbound:**
- `send_message()` sends direct message via instagrapi
- Text messages only initially

**Flow:**
```
Customer DM on Instagram → instagrapi userbot detects message → create complaint → pipeline → DM reply
```

**Key files:**
- `services/channels/instagram.py` — InstagramChannel (instagrapi client)

## Unified Closed-Loop Reply (Phase 6)

**Current state:** Only Telegram has hardcoded reply logic in:
1. `api/routes/complaints.py:298-321` — resolve reply
2. `agents/orchestrator.py:111-152` — triage notification

**Target state:**
- `respond_and_resolve_complaint` calls `channel_registry.send_response(complaint, text)`
- `merge_and_save` calls `channel_registry.send_triage_update(complaint, ai_draft)`
- Registry finds matching channel and calls `channel.send_message(source_ref, text)`
- All outbound messages logged to `outbound_messages` table
- No channel-specific `if` statements remain in route/agent code

**Channel-appropriate message formatting:**
| Channel | Max Length | Format | Triage Template Example |
|---|---|---|---|
| Email | None | HTML | Full branded email with ticket details |
| Telegram | 4096 chars | Markdown | Rich markdown with ticket ID, severity, SLA |
| WhatsApp | 4096 chars | Plain text | Concise ticket summary |
| Twitter/X | 280 chars | Plain text | Ticket ID + link to portal |
| Instagram | 1000 chars | Plain text | Ticket ID + link to portal |

## Sidecar Services (open-wa)

open-wa runs as a separate Node.js process. Added to `docker-compose.yml` as an optional service:

```yaml
openwa:
  image: openwa/openwa:latest  # or custom Dockerfile
  ports:
    - "8081:8081"
  volumes:
    - ./openwa-data:/app/data
  environment:
    - API_KEY=uccd_whatsapp_key
  restart: unless-stopped
```

For local development without Docker, the user runs open-wa separately via `npx @open-wa/wa-automate`.
